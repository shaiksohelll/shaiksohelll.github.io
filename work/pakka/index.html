01 / The hard problem

Escrow is not CRUD.

Two actors can ask the same system to move through a sensitive state at almost the same time. The system must decide who is allowed, which state is real, which balance is available, what gets recorded, and what survives a failure halfway through.

The design question How do you keep a browser retry, a concurrent request, or a disputed milestone from becoming two different truths?

The answer here Make the transition a named database operation with explicit actor checks, state guards, locks, constraints, and a ledger trace.

02 / System architecture

One request.
Four boundaries.

Read the architecture as text

User/client or worker → Next.js authenticated server action → Supabase Auth → RLS and RPC authorization → PostgreSQL transaction → milestone state, wallet balances, typed ledger, disputes and notifications.

Measurement boundary: a future typed event model; no current Pakka-specific lifecycle instrumentation is claimed.

04 / Database intelligence

The database is not storage.
It is the enforcement boundary.

Client state can describe an intention. It cannot be the final authority for a money-state transition.

Pakka moves sensitive decisions into named PostgreSQL functions, then layers RLS over the tables those functions touch.

01 / Permission

RLS narrows the room.

Owners and participants see and write only the records their relationship permits; administrator and service-role paths are separate.

02 / Function

RPCs name the move.

Four authenticated functions make fund, submit, approve/release, and dispute explicit operations with actor and state checks inside the boundary.

03 / Constraint

Indexes reject echoes.

Partial unique indexes guard one open dispute and operation-specific fund/release references, complementing—but not replacing—the function checks.

04 / Atomicity

Failure unwinds.

Wallet mutation, state change, and ledger insertion share a transaction boundary; later failure rolls back earlier statements.

Guarantee boundary

Local invariants are visible in the schema. A universal global balancing constraint, regulated custody, and production operational readiness are not claimed.

07 / Decisions

The tradeoffs are the work.

01

Database enforcement over client trust

Context
Browsers can retry, race, or hold stale state.
Decision
Put sensitive transitions behind PostgreSQL functions and constraints.
Why
The authority lives beside the rows it changes.
Tradeoff
More database logic to version, test, and explain.
Result
Invalid state is harder to express from the UI alone.
02

RLS plus explicit function authorization

Context
Table visibility and money movement are related but distinct decisions.
Decision
Use RLS for table access and in-function checks for transition authority.
Why
Two boundaries make the relationship legible.
Tradeoff
Policies and RPC checks must stay synchronized.
Result
Owners, participants, admins, and service paths remain explicit.
03

Operation-specific duplicate protection

Context
Funding, submission, release, and dispute have different retry shapes.
Decision
Use the guard that matches each operation instead of one universal idempotency slogan.
Why
Precision is more useful than a blanket claim.
Tradeoff
Each path needs its own test and failure explanation.
Result
Duplicate behavior is visible at the operation boundary.
04

Measure the product state, not just the click

Context
A click does not prove a funded, submitted, released, or disputed state.
Decision
Define a typed lifecycle event model before claiming product analytics.
Why
Engineering decisions should connect behavior to state.
Tradeoff
Instrumentation is an explicit next layer, not decorative telemetry.
Result
No unsupported traction story is presented.

Measurement boundary

Observed, not guessed.

This case study makes no product-traction claims because a Pakka-specific lifecycle event taxonomy was not verified at the 27 August 2026 audit snapshot. The next measurement layer is a typed event model covering contract creation, milestones, funding, submission, approval, release, disputes and failure paths.

08 / Production boundary

What I would harden before real money.

This is a reference implementation, not a regulated payment or custody platform. The next step is operational certainty—not more surface polish.

  • 01Payment boundary

    Integrate a regulated provider with verified webhooks and reconciliation.

  • 02Trust boundary

    Formalize KYC/AML, custody, fraud, and risk controls with the right compliance owner.

  • 03Evidence boundary

    Add stronger audit logging, disaster recovery, penetration testing, and fault-injection coverage.

  • 04Operations boundary

    Load-test contention, add monitoring and incident response, and define reconciliation runbooks.
